# 演进路线：从「插件」到「DSH 接管数据管理」

这份文件回答一个问题：**把 db-studio 做成插件之后，下一步往哪走？**

判断标准不是功能多少，而是一句话：**人还需要亲手点多少次鼠标**。每一次人从操作者退成审批者/旁观者，就是一次真正的接管。

---

## V1 —— 只读接管（当前版本）

**能力**：agent 能查元数据、跑查询；人能在面板里看见同样的东西。

- Host 半片拉起 Python sidecar，注册 10 个 `db_*` 工具。
- 只读连接白名单 + `WHERE` 拦截在服务端兜底；`allowWrites=false` 时写工具不出现。
- Client 半片：连接、元数据树、SQL 编辑器、结果网格、Redis 浏览。

**人能省掉的动作**：「帮我看下 X 表有哪些字段」「这个查询为啥慢，帮我看执行计划」「Redis 里 foo:* 还剩多少键」——不用再开 DataGrip。

**这一步的关键取舍**：先只开只读。接管的第一步不是"让 agent 能改数据"，而是"让 agent 能看数据"——看错方向的成本最低。

---

## V2 —— 写操作接管（审批即边界）✅ 已完成（第 21-24 轮，2026-11-11；Redis 明确不纳入，保持现状）

**能力**：agent 能改数据（工单 / 直执行 / 结构化行写），每次改动都过「审批 + 影响面预估 + 快照 + 窗口」四层边界。

1. **审批上下文够看** ✅：工单预估在 EXPLAIN 估算之外追加同条件 `SELECT COUNT(*)` 精确值（估算 ≤ 10 万才跑，`statements[].exact` 逐条标注）与 `plan`（访问类型/命中索引）；审批弹窗内嵌影响面摘要；direct 审批 payload 注入预估。
2. **变更前快照 + 撤销** ✅：写执行同事务抓受影响行落 `<dataDir>/undo/`（单语句 UPDATE/DELETE/INSERT，超 1000 行标记不可撤销不阻断，fail-closed）；`db_undo_last` 工具（direct 审批执行 / ticket 引导面板）+ 面板「撤销本次变更」按钮，撤销本身也快照 → redo 链。
3. **结构化行写** ✅：`db_write_rows` 工具（updates/inserts/deletes 结构化 diff，主键定位 + `%s` 参数化，≤200 行/次）；工单模式存 `rows_json`，审批人看 render 人读文本、执行走参数化；面板展示结构化 diff。
4. **会话写窗口** ✅：`allowWrites`（全局总闸，when 隐藏）之外的第二道时间闸——面板「临时开闸」15/30/60 分钟，到期自动关；四个 MySQL 写入口统一 403 `WRITES_CLOSED`（ADR D6）。

**验收感**：用户对一个写操作只做两件事——看一眼影响面、点「允许」；发现改错，再点一次「撤销」。

## V3 —— 去 sidecar（把 Python 收编进 Host）

**为什么**：sidecar 是 V1 的正确选择（复用已经打磨过的守卫/池化/Redis 兼容逻辑），但它是长期负担——多一个进程、多一套依赖、多一个启动失败点。

**做法**：在契约不变的前提下换实现。`src/host.js` 里所有工具都走同一组 `client.call(path, body)` 抽象，把传输层从 HTTP 换成原生 Node driver：

| 现在 | 之后 |
|---|---|
| `mysql2`（npm）替代 `pymysql` | 连接池 `core/pool.py` → `mysql2` pool |
| `ioredis` 替代 `redis-py` | `core/redis_pool.py` → `ioredis` |
| Python 的 `guard.py` | 直接移植到 `src/host/guard.js`（逻辑是纯词法，好搬） |

**关键**：`docs/CONTRACT.md` 的 API 形状不动，工具签名不动，面板不动。换实现不影响使用方——这就是当初把契约单独拆出来的原因。

**代价与收益**：多两个 npm 依赖；换来零 Python 环境依赖、进程少一个、冷启动从 ~1s 降到 ~50ms、Windows 上不再有 venv 路径问题。

## V4 —— 主动式数据管理

到 V3 为止，agent 还是"用户让它查它才查"。真正的接管是 **agent 自己知道该看什么**。

1. **巡检**：定期（`schedule_create`）跑一组体检——无主键表、超大表、慢查询（`performance_schema`）、连接数水位、Redis 内存与无 TTL 的大键——结果直接进会话或写一份 markdown 报告。
2. **变更风险评估**：agent 要改 schema 时，先自动算出"影响哪些查询/哪些下游"，把 DDL 当一次需要评审的改动来对待（配合 `worktree` 那套评审思路：先出 diff，再执行）。
3. **上下文注入**：把"当前会话牵连到的库表"通过 `ctx.systemPrompt.context` 自动带进提示词——用户说"给订单表加个字段"，agent 不用先问"哪个库"。
4. **多库编排**：跨 MySQL + Redis 的一致性问题（缓存与库不同步、双写顺序）是 agent 比人强的场景。

## 关键设计决策记录（ADR）

**D1 · 为什么是 sidecar 而不是直接重写**
旧后端里真正值钱的不是 HTTP 层，是 `guard.py` 的词法扫描、`pool.py` 的 SSCursor 流式取数与指纹失效、Redis RESP2 兼容这些踩过坑的细节。V1 的目标是**先把 agent 通道打通**，不是先重写数据层。重写放在 V3，且契约先行，保证可平滑替换。

**D2 · 为什么 Python 后端用 stdlib 而不是继续 FastAPI**
插件 sidecar 需要：启动快、依赖少、失败原因清楚。`ThreadingHTTPServer` 足够（QPS 是个位数）；砍掉 FastAPI/uvicorn 后依赖只剩 `pymysql` + `redis`，冷启动和排障都简单一档。

**D3 · 为什么浏览器不直连 Python 后端**
直连意味着令牌和连接密码要进浏览器，还要处理 CORS 与来源校验。Host 代理一层之后：浏览器只发同 origin 请求，凭证只存在于 Host 进程内，后端端口只绑 127.0.0.1——攻击面收窄到"本地进程间"。

**D4 · 为什么写工具用 `when` 隐藏而不是报错**
`allowWrites=false` 时把写工具从模型工具表里移除，比"注册着但一调就报错"更好：模型不会去尝试它、不会浪费 token 解释自己被拒绝、也不会因为看到写工具而产生"能不能绕过"的诱导。配置改了插件会重启，工具表随之重建。

**D6 · 为什么写窗口在运行时报错而不是工具隐藏（V2.4）**
全局 `allowWrites` 用 `when` 隐藏（D4）；会话级「临时开闸」若也走配置会重启插件、中断会话，若要 per-会话绑定又依赖宿主运行时（本仓库不可控）。折衷：写窗口落在后端 dbs.db meta（到期自动关），写工具注册着、执行时被 403 `WRITES_CLOSED` 拦截并在错误里给出「让用户在面板临时开闸」的可执行建议——工具可见但边界仍在，且无「开完忘关」（时间窗自动收口）。这是对 D4 的分层补充：隐藏管「能不能用」，窗口管「此刻让不让」。

**D5 · 为什么工具粒度是这样的**
`db_execute` 是一个工具而不是 `db_update`/`db_insert`/`db_delete` 三个：审批的语义是"这一条 SQL 要不要执行"，按语句类型拆工具只会让模型多绕一圈，且守卫本来就按语句类型判断。反过来 `db_redis_command` 保留"任意命令"形态——Redis 命令空间太大，枚举不现实，靠守卫 + 审批兜住。

## 暂不做（明确排除）

- **多用户 / 权限模型**：这是本地单用户工具的插拔，多租户是另一个产品。
- **把面板做成完整 IDE**：面板的定位是观测与轻操作，重度操作应该发生在对话里（让 agent 干），不是让用户回到点鼠标。
- **导出 xlsx/CSV**：等 V2 有了写入语义再一起做；导出属于"人拿走数据"的路径，agent 场景里直接返回结构化结果更合适。
